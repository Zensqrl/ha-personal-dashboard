# Huzband Dashboard v0.1 feedback and tweaks

Status: implemented and deployed in v0.1.1. The sections below preserve the collected requests and implementation reasoning. See `v0.1.1-implementation-plan.md` for release verification. Session-only dismissal is included; durable multi-device dismissal and an RHR baseline remain deferred.

## 1. All detail popups: show measurement time, not retrieval time

**Current behavior:** Each recovery metric shows text such as `Current source data · source 2026-09-21 · fetched 2026-09-22T00:09:20+00:00`.

**Meaning:** `Current source data` means the Garmin fetch succeeded and the value is neither retained from an earlier fetch nor fallback data. `source 2026-09-21` is the date Garmin assigns to the data. `fetched` is when Home Assistant checked Garmin, expressed in UTC; it is not necessarily the time the metric was measured.

**Requested change:** Replace technical provenance wording across Recovery, Training, Activity, Nutrition, and any other detail popups. Show `Measured 8:30am` (local `h:mmam/pm`, no seconds) **only when the source provides a verified measurement timestamp for that particular value**. Do not use Garmin `fetched_at`, Home Assistant state update times, or MyFitnessPal `retrieved_at` as substitutes for measurement time. Where only a day is known, show a plain day label such as `Today's Garmin value` or `Diary for today`; where neither measurement time nor day is known, omit the timestamp. Clearly label retained, fallback, stale, and incomplete values. An older reading may include its actual measurement date/time when available.

**Verified current limitation:** `src/model.mjs` currently passes Garmin `source_date` and `fetched_at` to the Recovery, Training, and Activity detail rows, and MyFitnessPal `retrieved_at` to Nutrition. These are source-day/retrieval metadata, not verified per-metric measurement timestamps. During implementation, inspect the live entity attributes and source payloads for true measurement timestamps; if absent, keep time hidden rather than implying one. Weather popup times are forecast-valid times and should retain their time meaning.

**Implementation location:** Detail rendering in `src/cards.mjs`; provenance and nutrition normalization in `src/model.mjs`; tests for true measurement time, day-only values, retained/fallback readings, and missing timestamps.

## 2. Weather tile: keep time together and quantify rain chance

**Current behavior:** On a narrow phone, `Rain risk around 9:00 PM` wraps immediately before `PM`. The phrase `Rain risk` does not convey likelihood.

**Requested change:** Keep the clock time and its `am`/`pm` designation together on one line, including at narrow phone widths. Show the forecast precipitation probability in the tile, for example `30% chance of rain around 9:00pm`. If the percentage is unavailable, use a clear qualitative label only when a defined mapping supports it; otherwise say the chance is unavailable rather than guessing.

**Verified implementation detail:** The tile already selects the first future hourly forecast with `precipitation_probability >= 30` and displays its `datetime`. The same forecast item supplies the exact probability. Update the tile copy and render its time as a nonbreaking unit; check the mobile layout at the screenshot width. Weather detail rows already display forecast probabilities.

**Implementation location:** Weather tile in `src/cards.mjs` and its mobile styling. Keep this as feedback for the later implementation plan; do not change the live dashboard during feedback collection.

## 3. Today's timeline: optional time-zone label

**Current behavior:** The timeline header always displays the Home Assistant time-zone identifier (for example, `America/New_York`).

**Requested change:** Add a card option such as `show_time_zone`, defaulting to `false`. Hide the label when the option is omitted or false; display the configured Home Assistant time-zone label when true. This option affects only the visible label. Event, forecast, and planning times must continue to use Home Assistant's time zone for conversion and scheduling.

**Implementation location:** The timeline header in `src/cards.mjs`, card defaults/config validation in `src/model.mjs` and `src/cards.mjs`, and the configuration example/documentation. Verify both default and enabled states.

## 4. Today's timeline: configurable planning-hour range

**Current behavior:** The footer displays planning hours, such as `8:00–21:00`. The card already accepts `start_hour` and `end_hour` options, defaulting to 8 and 21 in Home Assistant local time; the example dashboard does not demonstrate these options.

**Requested result:** Keep the planning-hour range configurable on the timeline card and make the configuration easy to discover in the card example and documentation. The footer should always reflect the effective configured range. Show it in a readable clock format consistent with the rest of the dashboard, including `am`/`pm` without separating the designator from the time. Confirm that changes affect both displayed hours and the underlying free-block calculations.

**Implementation location:** Existing options in `src/model.mjs` and validation in `src/cards.mjs`; document and exercise the timeline configuration in `dashboard.example.json` and README. No new scheduling option is needed.

## 6. Today's timeline: move planning notes into an expandable section

**Current behavior:** The timeline permanently displays `Planning hours 8:00–21:00. Suggestions reserve no time. Todoist calendars are excluded.` below the schedule.

**Requested change:** Put these notes in an expandable section, using the same interaction pattern as `How tasks are ranked` in Suggested Actions. The expanded text should show the configured planning hours and say plainly: `Suggested activities and tasks are only recommendations. ## 7. Suggested Actions: explain Todoist read failures and the next action

**Current behavior:** `Task data is incomplete, older or unavailable. Ranking resumes after a complete fresh read.` This collapses distinct causes into one message and gives no useful recovery step.

**Why it can happen:** The dashboard reads Todoist Enhanced through Home Assistant's `todoist_enhanced/tasks` WebSocket command. It suppresses rankings if the read fails or times out, the response contract is invalid, the last successful dashboard read is over 10 minutes old, or the integration reports stale/incomplete task or metadata enrichment. A temporary Home Assistant connection interruption or integration refresh problem can therefore cause this state even though Todoist itself still has tasks. The screenshot alone does not identify which condition occurred.

**Requested change:** Show the actual observed category and a proportionate next action. For a first read or temporary connection issue, say `Tasks could not be loaded. Try Refresh.` For an older cached read, say when it was last successfully checked and that ranking is paused until a new read succeeds. For incomplete/stale Todoist Enhanced data, say that the integration is still syncing and suggest checking its Home Assistant integration status if it does not recover after Refresh. If the command is unavailable or its response contract changed, identify the Todoist Enhanced integration as needing attention. Avoid suggesting reauthentication or reinstall unless that failure is specifically observed. Keep the dashboard read-only.

**Implementation limitation to address:** `src/controller.mjs` currently discards the actual read error, and `src/model.mjs` reduces all task readiness checks to one boolean. Preserve safe diagnostic categories (no secrets or raw task data), classify the failed readiness predicate, and render actionable text in `src/cards.mjs`. Add focused tests for each category and the healthy state. When inspecting the live instance, record which predicate produced the screenshot's state before claiming a root cause.

## 8. Header refresh: explain scope and show a result

**Current behavior:** The unlabeled circular-arrow button has only an accessibility label (`Refresh dashboard`). Tapping it calls the dashboard controller's poll method, but the screen gives no visible loading, success, skipped, or failure feedback. A poll may do nothing visible when data is unchanged, a read is already in progress, the page is hidden, a per-source cooldown has not elapsed, or failure backoff applies.

**Requested change:** Make the control's purpose clear in visible text or adjacent help: it checks dashboard inputs again; it does not force Garmin, Todoist, MyFitnessPal, calendar, or weather providers to sync upstream. On tap, provide immediate visible feedback such as `Checking data…`, followed by a concise result such as `Dashboard checked at 8:43pm`, `Already up to date`, or `Could not load Todoist tasks` as appropriate. When cooldown/backoff prevents a new request, say so instead of silently appearing unresponsive. Keep the refresh icon accessible, show a disabled/in-progress state, and do not falsely claim that underlying measurements changed.

**Implementation location:** Header button and status text in `src/cards.mjs`; structured poll outcome, per-source read results, and cooldown status in `src/controller.mjs`. Test both a successful read and a no-op/cooldown/failure path.

## 9. Recovery popup: simplify chart labels and replace boilerplate with useful context

**Current behavior:** The Body Battery chart's right time label adds `samples end`. The footer says `Thresholds are planning policy. No RHR normal/abnormal claim is made without a personal baseline.` Neither helps interpret the displayed readings.

**Requested change:** Show only the chart's start and end times; remove `samples end`. Remove the generic footer. Where reliable context exists, explain the relationship directly beside the relevant value: for example, compare last-night HRV with Garmin's balanced range, and say whether it is below, within, or above that range. Explain a recovery-related recommendation with the actual contributing values instead of a vague policy disclaimer. Keep resting heart rate as a plainly labeled value unless a verified personal baseline or trend is available. If such context becomes available, present the comparison and its source clearly; do not imply that a single RHR value is medically normal or abnormal.

**Rationale:** The current RHR caveat was added because the dashboard has no verified individual RHR baseline for interpretation. That caution belongs in the decision logic and documentation, not as unexplained user-facing text. The chart endpoint is already conveyed by the final time label.

**Implementation location:** `spark()` and Recovery detail rendering in `src/cards.mjs`; check Garmin values and any available RHR history before adding a trend comparison. Coordinate with tweak 1 for the remaining per-value source wording.

## 10. Suggested Actions: dismiss a recommendation and show the next task

**Requested change:** Give each suggested task a `Dismiss` action. Dismissing removes that recommendation from today's dashboard list and immediately fills its position with the next eligible ranked task, if one exists. It must not complete, delete, postpone, or otherwise modify the Todoist task. Make the action accessible and provide a simple way to undo an accidental dismissal.

**Feasibility:** Todoist Enhanced supplies a stable task `id`, and `rankTasks()` already computes a full ordered list before `actions()` shows only the first three. Filtering dismissed IDs before displaying the top three is straightforward. The same filter should apply to timeline task suggestions so a dismissed item does not reappear elsewhere on the dashboard. No new Todoist integration capability is needed.

**Scope decision for the implementation plan:** A session-only dismissal shared among dashboard cards is a reasonable v0.1 tweak; it resets when the dashboard session reloads. Durable, account-wide, or multi-device dismissal requires a persistence policy and synchronization and can be deferred to v0.2+. Do not store task content or a personal task snapshot in browser storage. If the expected persistence duration is clarified during planning, choose the smallest mechanism that satisfies it.

**Implementation location:** Shared dashboard controller or model state for a set of dismissed task IDs; ranking and timeline assignment in `src/model.mjs`; action button and undo feedback in `src/cards.mjs`. Verify replacement ordering, no duplicate timeline suggestions, undo, day/session reset, and no Todoist write.

## 11. Nutrition: show useful data-age bands and separate incompleteness

**Current behavior:** Nutrition is labeled broadly as `Older / incomplete` or `Older or incomplete diary`, without distinguishing a slightly delayed read from data that has been stale for hours. The available `retrieved_at` timestamp is when the diary response was retrieved, not necessarily when food entries were edited.

**Requested change:** Show the age of the displayed nutrition data using concise bands: more than 15 but less than 30 minutes, `>15 min ago`; 30 to under 60 minutes, `>30 min ago`; 60 to under 120 minutes, `>1 hr ago`; and 120 minutes or more, `>2 hr ago`. In user-facing copy, use a clear label such as `Nutrition data checked >15 min ago` or `Last retrieved >15 min ago` unless the MyFitnessPal source provides a verified last-update timestamp that justifies `Updated >15 min ago`. For data no more than 15 minutes old, retain a clear current-data label. If the diary day is not today, identify that separately. If totals or targets are missing, say `Incomplete nutrition data` independently of the age band, and do not imply that age alone caused incompleteness.

**Implementation detail:** Use the actual `retrieved_at` age already normalized in `nutrition()`; keep its existing 15-minute freshness requirement for decision logic unless a separate policy change is requested. Handle missing or invalid timestamps as unknown age, not as `>2 hr`. Show the same status consistently in the nutrition tile, signals card, nutrition popup, and any recommendation that relies on nutrition. Test boundary values at 15, 30, 60, and 120 minutes.
